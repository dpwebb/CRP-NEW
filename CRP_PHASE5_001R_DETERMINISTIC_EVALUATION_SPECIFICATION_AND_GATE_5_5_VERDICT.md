## 2. The report fact model and the status vocabulary (deliverables 1 and 2)

`report_fact_model.json` defines two facts of two kinds, and takes nothing about them on trust: every fact id,
label, locator, raw value, normalized value, binding rule and forbiddance is read out of the governed rule record
and the representation register at build time.

| --- | --- | --- | --- | --- | --- |

Each entry records **raw value, normalized value, source location, extraction status, event semantics and

recorded convention and may never be presented as a statutory date or as the date of any event.

`extraction_status_vocabulary.json` holds the gate's four statuses — `PRESENT`, `ABSENT_FROM_REPORT`,
`CONTRADICTED`, `EXTRACTION_UNRESOLVED` — parsed out of the gate line and matched against the four the
specification defines, with the builder refusing to write if the two sets differ. Each status records what it
is, every reachable path to it, and what it is not:

- `ABSENT_FROM_REPORT` has **exactly one** reachable path: the Collections section is located and resolved and
  prints no contract debt record. The reference date has **no** absence path at all;
- `CONTRADICTED` is reachable for the reference date when the header label is on every page but the printed
  values are not all identical, and is recorded as **unreachable** for the last-payment fact on this
  presentation, with its reason: the only way that fact can print two values is a label printed twice in one
  record, and the rule record's own binding rule maps that to `EXTRACTION_UNRESOLVED`;
- two states the earlier artifact carried as fact statuses — `UNSUPPORTED_PRESENTATION` and `NOT_A_DEBT_RECORD` —
  are kept in their **own layers**, so a refused document can never be read as an empty report and a region that
  is not a contract debt record is never read at all;
- the resolved state is named `PRESENT`, the gate's own word, with the equivalence to the record's `RESOLVED`
  recorded explicitly so the two names can never be read as two states;
- the recorded non-conflations are carried **verbatim**, and all six refusal states of the unit are named with
  the gate each one answers.

One refinement was reached this order rather than copied: where the section is resolved, prints no contract debt

## 3. The deterministic evaluator specification (deliverable 3)

`deterministic_evaluator_specification.json` specifies the evaluator, and `evaluator_001r.cjs` is its executable
form (rank 8, internal, not admitted, not wired to any application surface, reading no file and holding no
module-level state). The inputs are four and no more: the caller's **explicit** selection, the report's
**resolved facts and the observations they rest on**, the caller's **declared event-date mapping**, and the
**governed rule record** read as data. Nothing else is read — no clock, locale, time zone, host, session,
network or file.

The specification keeps four separable layers, as the phase bullet requires: **F1** status resolution, **F2** the
comparison, **F3** qualification, and **F4** the gate chain that composes them and decides emission.

**Six gates, in a fixed order.** `G1` selection supplied, `G2` selection is this unit's, `G3` presentation
eligibility, `G4` event-date mapping, `G5` no unresolved affirmative element, `G6` rule record admitted. Every
gate is evaluated and recorded, and the refusal is the **first failing gate** in that order — never whichever
failure happened to be noticed first. The unit-fit gates come first because they decide whether this unit may
read the input at all; the admission gate comes last because it bounds *emission* rather than reading, and
ordering it last keeps a deeper refusal observable instead of masking every input behind the one condition that
currently holds for all of them.

**Six conventions, carried as conventions.** `c1` the anniversary is the clock start plus six calendar years by
calendar addition; `c2` a 29 February start clamps to 28 February in a non-leap sixth year; `c3` the six-year
span in days is derived from the two dates and never hard-coded; `c4` elapsed time is whole days from the clock
start to the reference date; `c5` the period is exceeded when elapsed days exceed the span; `c6` **the exact
sixth-anniversary day carries no outcome.** Every one is recorded with `is_a_requirement_of_the_text: false`, so
none can quietly become a requirement of the statute.

**The arithmetic is recomputed, not restated.** On the governed record's own specimen dates the specification
yields anniversary `2027-02-01`, a `2,191`-day span, `1,919` elapsed days and `PERIOD_NOT_EXCEEDED` — the same
four numbers the rule record measured — and the 29 February clamp is exercised as arithmetic
(`2020-02-29` + six calendar years = `2026-02-28`).

**The boundary is withheld, and deterministically so.** The exact sixth-anniversary day is an exact date
equality tested **before** the greater-than branch, so it can never fall into `PERIOD_NOT_EXCEEDED` by accident
of ordering: it returns `UNRESOLVED` with `BOUNDARY_CASE_EXACTLY_AT_SIX_YEAR_ANNIVERSARY` and no outcome. The
internal comparator's contrary reading is **not adopted**, exactly as the rule record requires.

**What it refuses, and why the refusal is the operative behaviour.** Six named refusal states, one per gate.
Today, for every admissible input, `G6` fails — the governed rule record is **NOT ADMITTED** — so the evaluator
returns `REFUSED_RULE_RECORD_NOT_ADMITTED` with **no outcome**, and emits nothing. The specification states
plainly that the gate's "cannot emit on unapproved rules" is a *prohibition*, satisfied by a refusal that is
specified, implemented and tested, while the phase bullet's phrase "plus admitted rule records" presupposes an
admitted record this scope does not have. That presupposition is **named**, with the smallest action that would
settle it, and never converted into a criterion satisfaction.
