## 2. Startup / deployment procedure (existing — reused, not rebuilt)

1. The single process is `accelerated-launch/service/server.cjs`; it binds `CRP_LOCAL_SERVICE_HOST` (default `127.0.0.1`) on `CRP_LOCAL_SERVICE_PORT` (default `8787`). It never opens a public socket; a public origin must terminate TLS in front of it.
2. Start command (host-local): `node accelerated-launch/service/server.cjs` with the operator's environment file applied.
3. The process takes a single-writer lock inside `CRP_LOCAL_SERVICE_DATA` and **refuses to start** if that path resolves inside any checkout.
4. Static UI is served from the private UI tree only, through the committed allowlist (asserted by the release check).
5. Pre-release gate: `node -e "require('./accelerated-launch/service/release-check.cjs').runReleaseCheck({write:true})"` — local, read-only over the tree, makes no outbound call.
6. The prepared-but-unapplied deployment configuration is `accelerated-launch/service/deploy/` (README + `production.env.example` + the manifest generator). It contains **key names and fixed values only**; every secret is empty, deliberately, because the file is committed.

## 5. Rollback steps (existing procedure — reused)

1. Stop the process. The service writes **only** inside `CRP_LOCAL_SERVICE_DATA`: `state.json`, `state.json.bak`, `store.lock`, `blobs/`.
2. Point `CRP_LOCAL_SERVICE_DATA` at the previous data directory and start again. Nothing outside that directory is written — not the repository, not a system directory, not an external service.
3. A stale lock left by a dead process is taken over automatically; no manual cleanup step exists or is needed.
4. There is no schema migration and no destructive step, so rollback is a directory choice, not a data restore.
