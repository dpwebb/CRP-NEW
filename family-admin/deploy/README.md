## Existing independent portal procedure

Do not activate while Mail retains hosted release ownership. Obtain its final exact-build/configuration custody handoff first. Family Admin has its own immutable package, service, protected configuration, audit store, HTTPS router and rollback. Do not replace any existing app's runtime, environment, database, router or container.

Commit only `family-admin/`, then run its syntax and integration tests. `node scripts/package.mjs` refuses dirty source and copies every tracked Family Admin file into a new `.local/releases/crp-family-...` directory with exact byte hashes and the source commit. No credentials/configuration/audit data are packaged. Transfer the same complete directory to the VPS and independently run `verifyRelease` before installation. Hosted startup verifies the complete installed artifact and reports its release, commit and manifest hash in `/health`.

Before activation, inventory the three apps' existing builds, PIDs, images and protected environment hashes after Mail's handoff. Verify their existing health and app-specific roles. Save protected per-person binding evidence outside the source tree. Do not infer membership from email or use a shared credential. Staging bindings and production bindings are independent. Native sign-in is performed normally by each administrator; configuration does not create logged-in access.

Create dedicated unprivileged `crp-family-staging` and `crp-family-production` accounts without shell logins. Source releases are root-owned/read-only. Store configuration in `/etc/crp-family-admin/{staging,production}.json`, root-owned and readable only by the corresponding service group (0640). Each instance owns only `/var/lib/crp-family-admin-{environment}` (0700). Use the supplied systemd template; the listener remains loopback only. The sample proxy is staging-specific. Render a separately reviewed production proxy with admin.creditregulatorpro.com, listener18946 and app4396. Use separate exact-host Traefik router labels and its existing certificate resolver, without editing/restarting Traefik or existing routers. Pin the existing nginx image by digest. Add only the two previously absent DNS names; retain and compare every existing DNS record.

The first installation must refuse an existing service, directory, port, router name or DNS record unless a new reviewed operation explicitly expects it. Record a unique intent before activation and keep every failed attempt. Do not automatically rerun an uncertain installation. On an update, require the exact predecessor manifest/configuration hashes, stop only the Family Admin instance, snapshot its whole store/config/service/router, and preserve its journal/key. Never restore another app's database or configuration as part of Family Admin rollback.

Before production promotion, staging must verify TLS, exact asset hashes and health provenance, anonymous-data refusals, Host/Origin/CSRF, normal CRP password/MFA/admin unlock, both verified native application links, bounded roles/revocation, audit intents and responsive desktop/mobile views. Use new owned fictional staging records for any mutation and clean them normally. No payment or provider submission is necessary. Verify unknown outcomes without replay. Production must promote the identical accepted source package with production-specific protected bindings only, then verify authorized reads for all three apps and anonymous protection.

Back up the complete Family Admin store and configuration with authenticated encryption and an independently held recovery key. Recover into a separate temporary private directory and verify all bytes, permissions and the HMAC chain before considering the backup usable. Preserve the live integrity key and journal together. On crash, do not clear `process.lock` until the recorded process is proved exited. A journal integrity failure is a refusal, not a reason to create a fresh journal.

`scripts/backup.mjs pack <protected-context.json>` accepts `{config,audit,key,output,release}`; `recover <protected-context.json>` accepts `{backup,key,destination}`. The recovery key is an independently protected 32-byte file, never a command argument or repository value. AES-256-GCM authenticates the compressed private payload. Packing requires a stopped instance and validates the journal first. Recovery refuses an existing destination and verifies the original file hashes plus HMAC journal/unknown intents. Use a fresh private destination for each independent check; never overwrite the live store during verification. Windows fixture tests model 0600 metadata; real Windows key custody still requires private ACLs.

For a failed first activation, stop/disable only the new Family Admin service and remove only its exact owned router container; retain its private state, release, intent and logs for investigation. Remove new DNS records only by exact name/type/value after confirming they were created by this operation; never reset a zone. Existing native apps remain available throughout. Finish with exact preservation of their runtime, image and configuration inventory and independently qualify any normal monitoring/business changes; do not claim raw live database equality without evidence.


## Reboot-safe Linux locking
Read [LOCK_RECOVERY.md](../LOCK_RECOVERY.md). util-linux /usr/bin/flock is mandatory. Preserve process.kernel.lock as a persistent inode. Only a stopped, verified migration may quarantine the legacy process.lock after independent recovery. Never reset journal/key or start mixed old/new writers. Backup retains exclusive ownership through payload capture.
