# Persistent deletion custody and offline restore opening gate

The local `tools/implementation/deletion-custody.cjs` primitive stores an authenticated, ordered deletion receipt journal atomically under an explicitly supplied private directory and key. It refuses concurrent writers, collisions, malformed/tampered entries, missing files and unexpected file types. Receipts require an actual deletion-evidence hash; fixtures do not attest actual deletion.

Keep the latest signed anchor separately from the backup being restored. The offline gate requires that independently retained current anchor: an authentic old prefix alone cannot establish freshness. A missing, wrong-key, truncated or stale journal refuses. Reappearing account/case identifiers fail the deletion-identifier check without modifying the restored rows. Financial/provider/audit custody, approved PDFs, embedded identification and blobs still need their own approved reconciliation; a zero row count does not certify erasure. The primitive always returns serviceOpeningAllowed:false; it never authorizes opening a service solely because the supplied rows contain no deleted identifiers.

No existing delete endpoint, retention schedule, startup service or purge path is changed or activated. Integration must record intent before any native deletion, reconcile uncertain/partial outcomes, commit evidence only after verified completion, update independent custody, and run this gate before opening a restored service. Such integration must preserve current account-deletion rights and requires reviewed key custody, retention/hold policy and exact release acceptance. Keys and real deletion evidence are not invented in source. Actual source-state, blob and embedded-copy mutation remains disabled in this preparation batch.
